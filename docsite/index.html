What Worlds is

A small, self-hostable hosting platform for a team. Sign in with Google once, drop a folder, get a live URL. No pipelines, no keys, no infra. Inspired by Shopify's Quick.

  1. A folder with an index.html is a site. Add one tag and the whole platform is on window.worlds: 
    <script src="/worlds.js"></script>
  2. Deploy it with the CLI, drag-and-drop, or an MCP tool. It's live at https://<name>.your-worlds-host in a second. Re-deploy to overwrite.
  3. Use the batteries. worlds.db for documents, worlds.ai for the model, worlds.uploads for files, worlds.ws / room / rooms / actors for multiplayer, worlds.me() for who's here. Everything is scoped to your site automatically and gated by the sign-in wall.
What it's not for: public audiences, secrets (there are no permissions — anyone on the instance can read or overwrite any site), heavy compute, cron jobs, public webhooks. Inside the trust boundary it's deliberately simple; point the rest at a real backend.

Deploy a site

Three equivalent doors into the same POST /api/v1/deploy. Pick whichever is closest to hand.

# from the repo (or `bun run cli:build` once for a `worlds` binary)
bun cli/worlds.ts init my-site     # scaffolds index.html + .world.json
cd my-site && bun ../cli/worlds.ts deploy
# → https://my-site.your-worlds-host

The CLI tars the folder and posts it. worlds list shows every world; worlds open opens yours. Point it at this instance with WORLDS_HOST=your-worlds-host.

On the homepage, hit ✦ deploy a world and drop the folder onto the dialog. Same endpoint, no tooling.

# Claude Code
claude mcp add worlds --transport http https://your-worlds-host/mcp

The MCP server exposes deploy_site, delete_site, list_sites, get_site, my_sites, db_query, read_docs and search_docs. Auth rides your session cookie. More in Agents & MCP.

Optional .world.json

{ "description": "what this is", "category": "games", "spa_fallback": true }

Categories: games · work · tools · experiments · misc (default). They decide which star system your world orbits on the universe map. spa_fallback serves index.html for unknown paths.

Rules of the road

  • Reserved names you can't deploy to: api www home hello assets uploads list mcp docs u.
  • Relative URLs inside a site (./style.css); only /worlds.js is absolute. Sites also work in path-routing mode (/app/<name>/) that way.
  • Re-deploys overwrite. The deploy log (GET /api/v1/sites/<name>/deploys) is the audit trail. Only the first uploader can overwrite a site.
  • Delete a site you own from the ✕ on its homepage card, worlds delete <name> --yes, or the MCP delete_site tool (DELETE /api/v1/sites/<name>). Files, uploads, collections, documents and the deploy log go with it, and the name is free to deploy again.
  • Sites live forever without a rebuild: /api/v1 and /worlds.js are frozen, additive-only.

Two auth modes on the server: google (built-in sign-in; restrict by domain or email) or gateway (trust a verified-email header from oauth2-proxy / IAP / Cloudflare Access). Sites don't know or care which.

Database worlds.db

Named collections of JSON documents (≤256KB each), scoped to your site, with filters, sorting, atomic counters, optimistic concurrency and a realtime change feed over one multiplexed WebSocket.

a shared to-do boardopen this page in a second tab — every change streams across
const todos = worlds.db.collection("todos");
await todos.create({ text, done: false, votes: 0, by: me.name });
await todos.update(id, { done: true });          // shallow merge
await todos.increment(id, "votes", 1);          // atomic
await todos.delete(id);
const page = await todos.list({
  filter: { done: false },                        // eq, or {gt,gte,lt,lte,ne,in}
  sort: "-votes", limit: 20,                      // -field = desc
});
const stop = todos.subscribe(ev => {             // {type: create|update|delete, doc}
  render(ev);
});

    Cross-world reads worlds.db.site()

      Realtime channels worlds.ws

      A stateless topic broadcast: publish to a named channel, everyone subscribed gets it, nothing is stored. The right tool for chat, strokes, buzzers, reactions. Every channel also has presence.

      reactions…
      const ch = worlds.ws.channel("reactions");
ch.publish({ emoji: "🎉", cid: worlds.id() });      // ≤16KB, fire-and-forget
ch.subscribe(msg => {                                // { payload, from: {handle, name}, at }
  if (msg.payload.cid === worlds.id()) return;      // skip my own echo (optional)
  float(msg.payload.emoji, msg.from.name);
});
ch.presence(list => count.textContent = worlds.uniqByHandle(list).length);

      One shared room worlds.room

      The two things every multiplayer app re-implements, as one primitive: a roster (who's here, a stable host, ready toggles, start / back-to-lobby) and, if you pass initial, one authoritative document that's load-or-created, kept live and guarded against out-of-order writes. A waiting room is a room with no initial; a board game is a room with one.

      a shared pixel boardpaint in one tab, watch the other · roster is keyed by handle, so two of your tabs are one member
      const r = worlds.room("pixels", {
  initial: () => ({ cells: Array(64).fill(null) }),   // the shared doc
  minPlayers: 1, maxPlayers: 8, autoStart: false,
  onChange: s => render(s),      // roster OR state changed
  onStart:  s => begin(s),       // on every client
  onReturn: s => lobby(s),
});
await r.ready;
await r.merge({ cells: next });  // shallow-merge, monotonic; false on conflict → r.refetch()
r.toggleReady(); r.start(); r.returnToLobby(); await r.reset();
r.members; r.isHost; r.state;    // snapshot also has ready, readyCount, allReady, full, started, loaded

      Many rooms worlds.rooms

      The plural: a live directory of concurrent rooms with private join codes — a lobby browser. Each create / join / joinByCode hands back a normal worlds.room scoped to its own instance. Rooms whose host goes quiet are swept, so the list heals itself after closed tabs.

      tablescreate one here, join it by code from another tab or a teammate
      const hall = worlds.rooms("tables", {
  maxPlayers: 4,
  initial: () => ({ taps: 0 }),          // each table gets its own state
  onList: rooms => renderLobby(rooms),  // [{ id, code, name, host, members, count, max, status, private }]
});
const table = await hall.create({ name: "Enzo's table" });   // or { private: true }
const table = await hall.join(id);
const table = await hall.joinByCode("K7QF");
table.code; table.id; await table.merge({ taps: table.state.taps + 1 });
await hall.leave();     // leave the table, keep browsing
hall.destroy();         // tear the directory down

      Zoned presence worlds.actors

      The realtime tier for per-member state at frame rate, plus metadata and one-off events, all routed by the server only to peers in the same zone. Derive the zone from state (a grid cell) and you sync only nearby players no matter how many connect. A joiner gets an instant in-zone snapshot; the server rate-caps the flush.

      a field with six zonesmove your mouse · you only see peers in your cell · click to ping them
      const net = worlds.actors("field", {
  zoneKey: s => s.cell,           // same zone = see each other
  rate: 15,                        // server flush Hz (1..20)
  metadata: { team: "gold" },
  // observer: true,             // watch read-only, invisible to peers
});
net.set({ x, y, cell });                          // frame state, coalesced
net.setMetadata({ team: "teal" });                // infrequent fields
net.send({ t: "ping" });                          // event → in-zone peers
net.onChange((id, state, peer) => draw(peer));    // peer = {id, handle, name, state, metadata}
net.onEvent((id, payload, from) => ripple(id));
net.onLeave(id => remove(id));
net.others();  net.destroy();

      Collaborative documents worlds.doc

      One server-held CRDT document per name. The server keeps the authoritative Yjs copy, persists every accepted update before anyone sees it (commit before ack), checks each batch against the tree schema the site declares in .world.json under docs, and fans out to every subscriber. worlds.doc is the transport only: bring Yjs from a CDN and wire it in. worlds.docs.list() / remove() are the whole-document operations.

      a shared notepadtype in one tab, watch the other — every keystroke is a committed Yjs update
      import * as Y from "https://cdn.jsdelivr.net/npm/yjs@13/+esm";
const ydoc = new Y.Doc();
const t = worlds.doc("notepad", {
  onState:  (state)  => Y.applyUpdate(ydoc, state, "server"),   // initial load
  onUpdate: (update) => Y.applyUpdate(ydoc, update, "server"),  // a committed update (yours included)
  onAck:    (seq)    => …,                                        // yours is on disk
  onReset:  ()       => { t.close(); open(); },                   // the epoch moved: rebuild from state
  onRejected: (state, { rule }) => …,                             // schema violation: resync from state
});
ydoc.on("update", (u, origin) => { if (origin !== "server") t.send(u); });
const text = ydoc.getText("body");
text.observe(() => render(text.toString()));
await t.ready;  t.epoch;  t.seq;

await worlds.docs.list();   // this site's documents

      A rejected update never touches the live document, and a crash can only lose what nobody was told was accepted. Cursors and presence ride a normal channel (worlds.ws.channel("doc:notepad")). Services and agents use the same document over HTTP: GET /api/v1/docs/<name> → { epoch, seq, state }, POST …/updates, POST …/rotate to install a compact state as the next epoch.

      Idle progress worlds.idle

      The battery every tend-it game re-implements: remember when the player was last here, credit the (capped) time away, show a "while you were away" summary. The SDK owns the generic half; your game owns how its world advances over N seconds.

      while you were awayreload after ~10s to see a credited gap
      const idle = worlds.idle("docs-demo", { cap: 8 * 3600, min: 10 });   // cap/min in seconds
const secs = await idle.elapsed();           // capped seconds away, or null (first / too short)
if (secs) {
  const report = { dew: secs * 2, honey: Math.floor(secs / 60) };   // YOUR catch-up math
  idle.summary(report, { title: "While you were away" });          // self-contained modal
}
idle.beat();   // stamp lastSeen = now (also automatic on tab-hide / unload)
// store: "local" (default) | "db" (per-player doc) | "none" (you pass lastSeen)

      Errors WorldsError

      Every rejected promise is a WorldsError — { code, message, status, retryAfter? } — and code comes from a frozen registry, so you can branch on it forever. Session expiry redirects to sign-in and transient GET failures retry on their own; you never handle auth or flaky networks yourself.

      trigger onereal requests, real envelopes
      try { await c.create(doc); }
catch (e) {
  if (e.code === "quota_exceeded") worlds.toast("easy there!");
  else if (e.code === "conflict") await refetchAndRetry();
  else throw e;
}
// wire shape: { error: { code, message, retry_after? } }

      The v1 contract never breaks

      Deployed sites are never rebuilt, so /api/v1 and /worlds.js are frozen and additive-only: endpoints, fields and error codes are never removed, renamed or retyped. /worlds.js is the evergreen alias (served no-store so a new SDK reaches every site immediately); /v1/worlds.js is pinned and immutable. Your site works in five years without a rebuild. That's the whole deal.

      Caching

      Site HTML is no-cache with content-hash ETags, so an overwrite-deploy shows up on the next refresh and unchanged bytes 304. App code (.js/.css) is no-store; binary media gets a real max-age; anything under /vendor/ caches for a day. db / me / ai responses are never cached.

      How it works

      One Bun + TypeScript server with no runtime npm dependencies. It multiplexes by Host: <site>.<base> serves that site's files, the bare base is the homepage, /api/v1/* is the platform, and one WebSocket at /api/v1/socket carries every subscription, channel and presence on a page.

      Storage

      Postgres by default, or SQLite (WORLDS_DB=sqlite) to run the whole platform off one file — with optional S3 snapshots for durability. Both hold collections, the deploy log, profiles and the change feed.

      Files

      Sites and uploads sit behind a BlobStore seam: local disk by default, S3-compatible (AWS, R2, MinIO) when a bucket is set. Bundled apps ship in the image and reads fall through to them.

      Auth

      google: built-in sign-in, session cookie scoped to *.<base> so one login covers every site; restrict by domain or email. gateway: trust a verified-email header from your proxy.

      Routing

      subdomain (default) needs wildcard DNS + TLS. path serves sites at /app/<name>/ off one origin — no wildcard, works on free Cloudflare — trading per-site origin isolation. This instance: ….

      AI

      Gemini behind stable aliases, server-side key only. Streaming rides SSE. Embeddings feed the universe layout, so similar sites cluster as neighbouring planets.

      The universe

      The homepage is a 3D galaxy where every site is a planet, sized by visits and coloured by category. It's just another Worlds site on the public SDK, seeded on first boot.
